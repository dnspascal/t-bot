Part 1 — trend_follow
Break-even fires, logs success, and the broker never confirms it

Two trades in one overnight session — f21fd931 (-$4.63) and a69ed10c (-$6.16) — both had break-even activate mid-trade, both still closed at a real loss via the reversal watcher. On f21fd931: break-even moved the stop from 4415.20 to 4425.55 at 03:24:07 (peak gain $6.02 against a $5.82 trigger). Price later fell from 4425.44 (04:20) to 4423.81 (04:25) — straight through the new stop — and nothing closed the position. It sat open another 15 minutes until the watcher's regular 5-minute check force-closed it at 4420.70, well below where the "protected" stop should have fired.

Tracing it through the actual journal logs

Checked for a broker rejection first — none. Checked for the confirmation event the code already listens for — ORDER_REPLACED, logged as "SL/TP amendment confirmed by broker" — also never arrived. Confirmed DEBUG logging was enabled in production (so a silently-dropped/unrecognized frame would have shown too) and searched the exact 3-minute window around the amend: nothing came back from cTrader at all, not a confirmation, not an error, not an unrecognized frame.

AmendPositionSL → Connection.SendRaw writes the request to the socket and returns whatever the OS-level write error is — that's the entire extent of its "success" signal.
internal/provider/ctrader/api/connection.go:63-73

The bot logged "break-even stop set" and wrote the position_adjustments row purely because the network write didn't error — with zero verification that cTrader actually applied it. Checked against every break-even activation in history (31 total): most resolved fine (peak-drawback or a real breakeven_sl hit both closed correctly), but three — 470d4af9 (2026-08-13, -$2.47) and today's two — show the exact same signature: break-even "confirmed" in our own logs, then a real loss anyway via a mechanism unrelated to the stop that was supposedly active.

Decision — implemented and shipped

checkBreakEven now sends the amend and waits — on a separate goroutine, so a slow or absent broker response can't stall M1 processing for other positions — for the real ORDER_REPLACED event before marking BreakEvenActive or writing position_adjustments. Retries up to 3 times on timeout (5s each), then gives up loudly ("GIVING UP, position is running on its ORIGINAL stop, not newSL") instead of silently trusting an unconfirmed amend for the rest of the trade's life.

What had to change to make this possible

ORDER_REPLACED events didn't carry a position ID before — nothing could route a confirmation back to the specific position waiting on it. Threaded a PositionID through the proto decoder (decodeFullExecutionEvent), the client layer, and the provider translation layer, plus a pendingBreakEven map[string]chan struct{} on Bot that onExecution's ExecOrderReplaced case signals into.

case config.ExecOrderReplaced:
    slog.Info("SL/TP amendment confirmed by broker", "brokerOrderID", exec.BrokerOrderID, "posID", exec.PositionID)
    b.signalBreakEvenConfirmed(exec.PositionID)
    return

internal/bot/watcher.go, internal/bot/bot.go, internal/bot/registry.go, internal/provider/{provider.go, ctrader/ctrader.go, ctrader/api/{client.go, proto.go}}. Shipped as fix: confirm break-even SL amendment with broker before trusting it via feat → dev (squash) → main (merge) → tag, deployed through the CI/CD pipeline (Part 6 covers finding that pipeline — this fix and the breakout fix below were the first two to actually go out through it).

Tightening the stop shrinks average loss ~2x at flat expectancy; a "lock in gains" rule makes it worse

Separate question from the above: not "should trend_follow enter differently," but "once a trade is open and going to lose, can the loss itself be made smaller." Two real per-trade levers, full-history backtested on trend_follow's relaxed-gate entries with real cooldown simulation:

Expectancy stays flat (~$7.5/trade) across every tested SL distance — win rate drops, but a fixed TP means the R:R improves proportionally, netting out even. Tightening to 0.75× ATR nearly halves the average loss ($7.79 → $3.88) for effectively no cost to overall profitability. This is the one lever tested today that looks close to free.

Part 4 — breakout
SL anchored to a stale breakout level, TP anchored to the live entry price

Flagged from a real trade: #237373667, XAUUSD SELL, opened and closed in 55 seconds via sl_hit, net -$2.41. SL was $2.21 away; TP was $17.92 away — an 8:1 ratio, nowhere near the strategy's intended 1.0×ATR / 2.0×ATR (a 2:1 shape). Price fell almost $40 past where TP was within the next hour — the setup was right, the stop just wasn't sized the way the code thought it was.

if dir == config.SignalBuy {
    slPrice = level - slATRMult*atr        // stale — from the signal-detection bar
    tpPrice = currentPrice + tpATRMult*atr // fresh — from the actual entry bar
} else {
    slPrice = level + slATRMult*atr
    tpPrice = currentPrice - tpATRMult*atr
}

internal/strategy/breakout/strategy.go:152-158 (before fix). Entry only fires after "await next-bar confirmation" (Evaluate's pendingDir flow) — by construction, price has already moved from level by the time tryEnter runs. The only guard was slPips < 3, a bare non-zero floor that doesn't check the realized risk against the intended ATR distance at all. The faster and more genuine the breakout, the more currentPrice has moved from level — meaning the bug is worst on exactly the trades that would otherwise have worked best.

Checked today's other 2 breakout trades for the same pattern — both had normal ~$11-12 SL distances, so this is real but intermittent, not universal: it only bites when price has drifted meaningfully between level-detection and confirmed entry.

Decision — implemented and shipped

SL now anchors to currentPrice, same as TP — matching how dd_ranging_breakout and dd_early_breakout (checked directly, confirmed already correct) construct both sides. level is still used for the entry-confirmation check itself (did price stay past the level after next-bar close) — that logic is untouched, only the stop-distance calculation changed. Shipped as fix: anchor breakout SL to currentPrice, not the stale breakout level.

Part 5 — Checking the other 8 strategies
Two more share the pattern — neither gets the same fix

Read every strategy's SL/TP construction directly rather than assume breakout was the only one. Clean — both sides anchor to currentPrice: trend_follow, rsi_reversal, dd_ranging_breakout, dd_early_breakout, sr_bounce, session_momentum, dd_oversold_bounce. Two more have the same structural shape as breakout — SL and TP reading from different reference prices — but each is a genuinely different problem, not a copy of the same bug:

session_open — SL anchors to the far side of the entire pre-session range Open

slPrice = m15.SessionLow - slATRMult*atr for a BUY, vs. tpPrice = currentPrice + rangeSize*tpRangeMult. Unlike breakout's level, the session range boundary is stable for the whole session — not recalculated per bar — so this doesn't have breakout's "drifts arbitrarily by entry time" problem. It looks like a deliberate design ("if price fully reverses through the whole range, the thesis failed"), but the realized risk is often much wider than a plain 1×ATR stop — range width plus overshoot plus buffer — the opposite failure mode from breakout. Not touched pending a decision on whether the wide stop is intentional.

ema_pullback — TP targets the recent H1 extreme, no ATR relationship at all Open

slPrice = h1.EMASlow ± slATRMult*atr, tpPrice = h1.TrendHigh (or TrendLow). SL is reasonably bounded in practice — the entry gate already requires currentPrice within 1×M5-ATR of the EMA before it'll signal, so SL-from-EMA can't drift far from SL-from-currentPrice. TP is the real gap: there's no tpATRMult constant in this file at all — reward is whatever the rolling 20-bar H1 high/low happens to be, checked only against a bare tpPips < slPips → hold floor. Reward size is inconsistent trade to trade: sometimes a real target, sometimes barely past breakeven, sometimes unrealistically far. This may explain ema_pullback's previously-flagged, unresolved 5.1% simulated win rate from the 2026-08-17 price-action investigation — an inconsistent, sometimes-unreachable TP is a plausible cause, not confirmed.

Neither is a "just copy the breakout fix" situation — both look like deliberate, just-uncalibrated design choices. Left as-is pending dedicated investigation (real trade history + backtest, same rigor as breakout) for each.

Part 6 — Dashboard, and finding the real deploy path
Trade-detail chart overhaul, plus a wasted hour that a five-minute check would have avoided

Trade-detail page now shows: entry/peak/adverse/exit as distinct markers (color legend, not inline text — text labels collided whenever markers land close together, which is common on short trades), SL/TP lines always visible (previously could render entirely off-screen if price never approached a distant TP), a "CLOSED" divider, and — the main ask — 4 hours of real candle data past the close, so a trade's chart shows what price actually did after the bot exited.

Peak/trough markers could land after the close line Fixed

Marker candles were picked by "closest candle to this price" searched across the entire loaded window — once that window included 4 hours of post-close data, a coincidentally similar post-close price could steal the "PEAK" marker onto a point in time after the trade had already ended, which is factually impossible (peak favorable is a fact about the trade while open). Caught by testing a second real trade, not assumed from the first. Fixed by restricting the marker search to pre-close candles only.

Markers on short trades silently vanished — Recharts drops any point that doesn't land on a real candle Fixed

A 5-minute trade's entry/peak/adverse/exit can all resolve to the same 1-2 M5 candles. Spreading them apart with arbitrary continuous time offsets (in seconds) made 3 of 4 markers disappear from the DOM entirely — no error, no console warning. Root-caused by inspecting the actual rendered SVG directly rather than guessing further: the X-axis is a discrete category scale (one tick per real candle), and any ReferenceDot x-value that doesn't land exactly on one gets silently discarded. Fixed by spreading markers in candle-index space (snap to the next real candle) instead of continuous time.

Manual API deploy got silently reverted by the real CI/CD pipeline Fixed

Deployed the 4-hour-window cmd/api change by hand (cross-compiled, scp'd, restarted the service) before discovering .github/workflows/deploy.yml already exists — triggers on any v* tag push, builds on a native Linux GitHub runner (no cross-compile problem there at all), and deploys+restarts all three services. The next tag push (for the breakout fix) rebuilt cmd/api from git HEAD, which didn't have the uncommitted manual change, and silently overwrote it back to the old 10-minute window. Caught by re-verifying live on the production dashboard rather than assuming the earlier manual deploy still held. Fixed by committing the change properly and re-tagging — confirmed on the real production site afterward (close_at 04:40, last candle 08:40, exactly +4h).

Net effect going forward: the trading-bot binary and the API binary both deploy through git tag v* → GitHub Actions, not local cross-compilation. The earlier struggle to cross-compile cmd/bot locally (blocked on ONNX/CGO, never resolved) was solving a problem that didn't need solving.
