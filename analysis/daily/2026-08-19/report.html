Part 1 — Break-even amend
Every break-even amend on gold was being rejected by the broker — floating point noise, not a broken confirmation path

Pulled 7 days of gold journal logs looking for the confirmed-vs-actual gap the 2026-08-18 fix was meant to close. Found something upstream of that instead: every single real break-even attempt in the window — dozens of them, across every process restart — failed with INVALID_REQUEST ("more digits than allowed") or TRADING_BAD_STOPS ("Allowed 2 digits"). Confirmation was never the problem; the amend was never being accepted in the first place.

newSL: 4335.110000000001 sent to a symbol that only allows 2 decimal digits.
internal/provider/ctrader/api/client.go — AmendPositionSL, before fix

Order-open SL/TP already rounds correctly (encodeNewOrderReq, via a priceDecimals-derived scale) — that path was never affected. The amend path never got the same treatment: it sends an absolute price as a raw float, and nothing snapped it back onto the symbol's tick grid before it went on the wire.

First fix attempt used the wrong reference number, and looked correct by coincidence Caught before shipping wrong

Rounded against c.priceDivisor — the raw spot-quote wire scale (1/100000, same for every symbol) — instead of the symbol's actual tradable precision. The first live test (a real trade whose newSL was built purely from OpenPrice + a clean pip buffer) passed, because that value only carried float noise past the 5th decimal, which the wrong rounding happened to catch anyway. A second test — newSL built from a live mid-quote instead of a clean fill price — carries genuine 3rd-decimal precision that isn't noise, and sailed straight through un-rounded. Corrected to round against priceDecimals (the same value encodeNewOrderReq already uses), confirmed via journalctl: broker confirmation in 96ms, first attempt.

Decision — implemented and shipped

AmendPositionSL rounds newSL/tp to the symbol's tick size before encoding. Verified against a real live trade the same day: break-even amend sent, confirmed by broker, position protected — the first successful break-even confirmation on gold in the entire week of logs checked.

Part 2 — Telegram routing
Gold couldn't receive commands at all — found while building the tooling to test Part 1

Needed /testamend to validate the fix live without waiting for a real trade to cross the break-even trigger. It never reached gold. Gold and EURUSD share one Telegram bot token and one webhook port, and the reverse proxy (Caddy) statically forwards the whole domain to a single backend port — registration order at the Telegram API level was irrelevant, since only one process was ever actually listening on the port Caddy points at. Every command landed on EURUSD regardless of which bot last restarted.

Decision — implemented and shipped

Gave gold its own dedicated webhook port and secret. EURUSD temporarily lost inbound command access as a trade-off — flagged as an open item below, not resolved today.

Part 3 — Peak-drawback math
Percentages above 100% on peak-drawback closes — EURUSD only, never gold

Some closed trades logged a "gave back 107%" or "201%" of their peak — a number that should be capped near 100 by construction. Pulled the full 30-day distribution before assuming anything about the cause:

SymbolPeak-drawback closesAvg %Max %Over 100%
EURUSD1797.5%201%8 (47%)
XAUUSD4267.8%149%2 (5%)

The formula divided the amount given back by how far the trade's peak actually got (peakGain) — a number that's small and unstable right after a trade barely clears its 70% gate. Checked why this lands on EURUSD specifically rather than assuming: EURUSD's median TP distance is 14 pips against gold's 194 — over 13x smaller — so the same ordinary tick-to-tick noise that's negligible on gold becomes a large swing on EURUSD once divided by such a small base.

Decision — implemented and shipped

Divide by tpDist (distance to TP, fixed at trade open) instead of peakGain. Same style of percentage, same intuitive reading, but the denominator can no longer collapse toward zero just because a trade barely cleared the gate.

Root mechanism: watchPositions only runs once per M5 candle close — every 5 minutes — and its regime signal is an EMA crossover, a lagging indicator by construction that only flips after price has already moved. But checking 4 of the fastest cases individually showed something more specific: those closed within 4–5 minutes of opening, at the very first check opportunity, and had already burned 27–57% of their stop room by then. So the problem isn't purely check frequency — gold can move fast enough that some reaction lag is structurally unavoidable regardless of how often the check runs.

Part 6 — session_open
SL/TP sized off a single pre-session clock hour, with no ceiling

Two gold trades today opened with a $105.70 / $107.69 stop-loss — full position size, same as every other trade, on a ~$400 account. Traced the mechanism rather than assume a data glitch: pulled the actual M15 candles for the pre-session accumulation hour and confirmed a genuine $80.30 range (gold rallied from ~4362 to ~4442 within that single hour) — real market action, not corrupted data.

if dir == config.SignalBuy {
    slPrice = m15.SessionLow - slATRMult*atr        // anchored to the hour's low
    tpPrice = currentPrice + rangeSize*tpRangeMult  // range had no ceiling
} else {
    slPrice = m15.SessionHigh + slATRMult*atr
    tpPrice = currentPrice - rangeSize*tpRangeMult
}

internal/strategy/session_open/strategy.go (before fix). The strategy's premise is a calm pre-session consolidation before a clean breakout — nothing checks whether that premise actually held for the specific hour in question. When real volatility lands inside the accumulation window instead, both SL and TP scale up together, proportionally, unconditionally. Both trades closed safely at +$28–29 via the reversal watcher before the stop was ever tested — a lucky outcome, not a protected one.

Decision — implemented and shipped

Switched SL/TP sizing to ATR off the current price — the same pattern already used by trend_follow and the rest. The breakout entry logic (price crossing the pre-session range) is untouched; only the sizing basis changed.

Part 7 — Exit thresholds
Break-even trigger lowered to 25%, and a new stall detector — both derived from real trade data, not picked by feel

Two of today's losing trades (28.7% and 32.7% of the way to TP) reversed just under the old 33% break-even line before protection could ever engage. Lowered breakEvenTriggerPct to 25% — would have protected both.

Separately: the existing 30-minute "zero favorable movement" time-stop only catches a trade pinned at literally 0% progress. It misses trades that show a little promise (1–14% of TP) and then go nowhere — one gold position sat for 130 minutes, having peaked at 28.7%, before the reversal watcher finally caught it. A candidate fix needed a real threshold, not a guess — first instinct (20–25 minutes) turned out to be far too aggressive once checked against data:

60 minutes only risks prematurely cutting the slowest 5–10% of genuine winners. Before shipping it as a replacement for the 30-minute check, tested that assumption directly: pulled the one real gold case that triggered the 30-minute check in the last 30 days (-$39.02) and checked what price did in the following 30 minutes had the bot waited instead — it kept sliding, to -$44.47 at its worst. Waiting longer would have cost more, not less, for the pattern that check exists to catch (a position pinned at 0% favorable can be actively bleeding the whole time, which staying flat on MaxFavorable doesn't rule out).

Decision — implemented and shipped

Kept both checks, run separately: the existing 30-minute/0% check (fast reaction to the worst pattern), plus a new 60-minute/15%-of-TP stall check alongside it (broader net, slower trigger) — closing as time_stop=stalled_60m. Both timeouts, the stall threshold, and the new break-even trigger are recorded in decisionParams() so every trade's own snapshot carries the values that were live when it opened.
