Commit 248153c switched cTrader SL/TP encoding to the relative-field format (fields 19/20, ×100000 — correct per the Open API spec) but dropped the step that rounds the distance to the symbol's real tradable precision first. Gold trades in $0.01 ticks; the un-rounded distance produced values that don't align to that tick grid, so every single XAUUSD order errored with "Relative stop loss has invalid precision" from 2026-08-11 22:10 onward — 28 straight failures, EURUSD unaffected (its 5-decimal precision already aligns 1:1 with the ×100000 scale). Fixed by restoring the precision-rounding step, now applied to the relative-field path.

Break-even SL amend was silently deleting the take-profit Fixed

encodeAmendPositionSLTPReq only ever sent the stopLoss field (4) since it was first written. cTrader clears the existing takeProfit when the amend request omits it, rather than preserving it — confirmed live: a trade ran to +$39 of favorable excursion, past where TP should have closed it, because TP no longer existed on the position after break-even fired. Affected every symbol/provider, not just gold. Fixed by resending the tracked TP price (field 5) on every SL amend.

Both shipped via feat → dev (squash) → main (merge) → tag and deployed at 03:22 EAT. Confirmed live: gold's next signal filled correctly with SL/TP intact.

Part 2 — Strategy review
dd_ranging_breakout: what the backtest said vs. what happened live

While confirming the gold fixes, a trade closed via sl_hit after 27 seconds, net -$2.08. Checking further, this wasn't a one-off — it's a pattern specific to one strategy.

"Data-driven strategy derived from 55-day signal analysis (v2_condition_analysis_2026-08-04). Condition group: H1=ranging, M5=breakout, M5 EMA bull, M5 RSI mid-high (≥50) → 60–64% BUY win at 4h (n=59–71)."
internal/strategy/dd_ranging_breakout/strategy.go:11-13

Based on that backtested win rate, the strategy was tuned for a 3:1 reward:risk shape — TP = 1.5×ATR, SL = 0.5×ATR — deliberately tight, on the assumption that a ~25% win rate would already break even, and 60–64% would be comfortably profitable. Its sibling dd_oversold_bounce came from the same backtest run with the same 0.5×ATR SL, on a condition group reported at 70.6% (n=34).

What the backtest missed

The condition-analysis script simulates each signal's outcome by scanning candles for a TP or SL touch:

startIdx := sort.Search(len(sc), func(i int) bool {
    return sc[i].BarTime.After(m.CreatedAt)   // starts AFTER the signal's own bar
})
// ...loop uses M5 (5-minute) candle High/Low for hit detection, from startIdx onward

analysis/v2_condition_analysis_2026-08-04/main.go:219-221

Two compounding gaps:

  1. It never checks the entry bar itself. The scan starts at the first M5 bar strictly after the signal's CreatedAt timestamp — so any reversal in the seconds immediately following entry, still inside that same bar, is invisible to the backtest. That's precisely where live trades are dying: 9s, 27s, 1m43s after entry.
  2. Hit detection is 5-minute-bar granularity. Even for subsequent bars, the backtest only knows a bar's High/Low touched TP or SL — not the order, speed, or path price took to get there. A stop that's half an average bar's range sits well inside ordinary tick-to-tick noise, which a 5-minute bar can't resolve.

The 60–64% figure is real for the question the backtest actually asked ("does price reach TP before SL within 4 hours, starting one bar after entry") — it just wasn't the question that matters for a 0.5×ATR stop, which lives or dies in the seconds right after entry, not four hours later.

Decision — implemented and shipped

dd_ranging_breakout: widen SL from 0.5×ATR to 1.0×ATR (matching the next-tightest strategies in production, all of which show zero fast SL hits). Strong live evidence: 59% SL-hit rate, net loser, exact failure mode explained above.

dd_oversold_bounce: same backtest lineage, same blind spot, but zero live trades — no track record to lose. Recommend widening preemptively to 1.0×ATR rather than waiting to reproduce the same failure live.

session_open: not from this backtest, different entry logic (session-range breakout, not ATR-chase off current price), and shows none of this pattern live (near-breakeven, only 1 of 13 trades an SL hit and not a fast one). No evidence it needs changing — leave as is.

How we're fixing it

One-line constant change in each strategy file — TP stays at 1.5×ATR, only the SL multiplier moves:

const (
    tpATRMult = 1.5
-   slATRMult = 0.5
+   slATRMult = 1.0
)

internal/strategy/dd_ranging_breakout/strategy.go:19-21 and the equivalent constant in internal/strategy/dd_oversold_bounce/strategy.go.

This drops the reward:risk ratio from 3:1 to 1.5:1 — still solidly profitable at anywhere near the backtested 60–64% win rate (breakeven point moves from ~25% to ~40%, and the observed live win rate was already 40.6% even while getting clipped by noise). The real fix is giving the stop room to sit outside ordinary intrabar movement instead of inside it, which is what was actually costing trades — not the win rate itself.

No other logic changes: entry conditions, TP distance, and position sizing stay exactly as backtested. Ships through the same feat → dev (squash) → main (merge) → tag flow used for today's other two fixes, once you confirm scope.
