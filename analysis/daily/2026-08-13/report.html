Part 1 — Production fixes shipped today
Gold stopped trading, then stopped protecting itself
XAUUSD orders rejected with INVALID_REQUEST since last night's deploy Fixed

Commit 248153c switched cTrader SL/TP encoding to the relative-field format (fields 19/20, ×100000 — correct per the Open API spec) but dropped the step that rounds the distance to the symbol's real tradable precision first. Gold trades in $0.01 ticks; the un-rounded distance produced values that don't align to that tick grid, so every single XAUUSD order errored with "Relative stop loss has invalid precision" from 2026-08-11 22:10 onward — 28 straight failures, EURUSD unaffected (its 5-decimal precision already aligns 1:1 with the ×100000 scale). Fixed by restoring the precision-rounding step, now applied to the relative-field path.

Break-even SL amend was silently deleting the take-profit Fixed

encodeAmendPositionSLTPReq only ever sent the stopLoss field (4) since it was first written. cTrader clears the existing takeProfit when the amend request omits it, rather than preserving it — confirmed live: a trade ran to +$39 of favorable excursion, past where TP should have closed it, because TP no longer existed on the position after break-even fired. Affected every symbol/provider, not just gold. Fixed by resending the tracked TP price (field 5) on every SL amend.

Both shipped via feat → dev (squash) → main (merge) → tag and deployed at 03:22 EAT. Confirmed live: gold's next signal filled correctly with SL/TP intact.

Part 2 — Strategy review
dd_ranging_breakout: what the backtest said vs. what happened live

While confirming the gold fixes, a trade closed via sl_hit after 27 seconds, net -$2.08. Checking further, this wasn't a one-off — it's a pattern specific to one strategy.

"Data-driven strategy derived from 55-day signal analysis (v2_condition_analysis_2026-08-04). Condition group: H1=ranging, M5=breakout, M5 EMA bull, M5 RSI mid-high (≥50) → 60–64% BUY win at 4h (n=59–71)."
internal/strategy/dd_ranging_breakout/strategy.go:11-13

Based on that backtested win rate, the strategy was tuned for a 3:1 reward:risk shape — TP = 1.5×ATR, SL = 0.5×ATR — deliberately tight, on the assumption that a ~25% win rate would already break even, and 60–64% would be comfortably profitable. Its sibling dd_oversold_bounce came from the same backtest run with the same 0.5×ATR SL, on a condition group reported at 70.6% (n=34).

Every strategy running SL ≥ 1.0×ATR has zero fast SL hits, regardless of its overall win rate. Only the 0.5×ATR strategies show sub-5-minute stop-outs — and of those, only dd_ranging_breakout has live trades to show it: 40.6% observed win rate against a 60–64% backtested one, and a net loss where the backtest implied a clear edge.

What the backtest missed

The condition-analysis script simulates each signal's outcome by scanning candles for a TP or SL touch:

startIdx := sort.Search(len(sc), func(i int) bool {
    return sc[i].BarTime.After(m.CreatedAt)   // starts AFTER the signal's own bar
})
// ...loop uses M5 (5-minute) candle High/Low for hit detection, from startIdx onward

analysis/v2_condition_analysis_2026-08-04/main.go:219-221

Two compounding gaps:

  1. It never checks the entry bar itself. The scan starts at the first M5 bar strictly after the signal's CreatedAt timestamp — so any reversal in the seconds immediately following entry, still inside that same bar, is invisible to the backtest. That's precisely where live trades are dying: 9s, 27s, 1m43s after entry.
  2. Hit detection is 5-minute-bar granularity. Even for subsequent bars, the backtest only knows a bar's High/Low touched TP or SL — not the order, speed, or path price took to get there. A stop that's half an average bar's range sits well inside ordinary tick-to-tick noise, which a 5-minute bar can't resolve.

The 60–64% figure is real for the question the backtest actually asked ("does price reach TP before SL within 4 hours, starting one bar after entry") — it just wasn't the question that matters for a 0.5×ATR stop, which lives or dies in the seconds right after entry, not four hours later.

Decision — implemented and shipped

dd_ranging_breakout: widen SL from 0.5×ATR to 1.0×ATR (matching the next-tightest strategies in production, all of which show zero fast SL hits). Strong live evidence: 59% SL-hit rate, net loser, exact failure mode explained above.

dd_oversold_bounce: same backtest lineage, same blind spot, but zero live trades — no track record to lose. Recommend widening preemptively to 1.0×ATR rather than waiting to reproduce the same failure live.

session_open: not from this backtest, different entry logic (session-range breakout, not ATR-chase off current price), and shows none of this pattern live (near-breakeven, only 1 of 13 trades an SL hit and not a fast one). No evidence it needs changing — leave as is.

How we're fixing it

One-line constant change in each strategy file — TP stays at 1.5×ATR, only the SL multiplier moves:

const (
    tpATRMult = 1.5
-   slATRMult = 0.5
+   slATRMult = 1.0
)

internal/strategy/dd_ranging_breakout/strategy.go:19-21 and the equivalent constant in internal/strategy/dd_oversold_bounce/strategy.go.

This drops the reward:risk ratio from 3:1 to 1.5:1 — still solidly profitable at anywhere near the backtested 60–64% win rate (breakeven point moves from ~25% to ~40%, and the observed live win rate was already 40.6% even while getting clipped by noise). The real fix is giving the stop room to sit outside ordinary intrabar movement instead of inside it, which is what was actually costing trades — not the win rate itself.

No other logic changes: entry conditions, TP distance, and position sizing stay exactly as backtested. Ships through the same feat → dev (squash) → main (merge) → tag flow used for today's other two fixes, once you confirm scope.

Part 4 — breakout strategy
Two separate bugs: false-breakout entries, and no limit on piling up during a losing streak

Prompted by a specific trade: XAUUSD SELL opened 10:20, closed 10:48 via sl_hit, net -$12.45. max_favorable was only $0.40 from entry before it reversed and ran the full distance to the stop — barely any breathing room before the trade went wrong.

Bug 1 — a single candle was enough to confirm a "breakout"

BreakoutLevel (internal/indicator/structure.go:39-67) looks at the prior 10 M15 candles (2.5 hours), takes the highest high and lowest low across them — call that the recent range. The moment the newest candle's high or low pokes past that range and its close also ends up beyond it, the old strategy treated that as a confirmed breakout and traded immediately. No requirement that the move hold beyond that one candle.

Across all 32 closed breakout trades ever, 18 (56%) show the same signature — barely move favorably before reversing:

Close reasonTradesAvg duration Avg % of SL distance reached favorablyNet P&LClosed within 5min
reversal_signal_bail96.1 min 17.3%-$0.285 of 9
sl_hit951 min 44.7%-$23.711 of 9
peak_drawback99.2 hrs 267.3%-$2.140
tp_hit229 min 244.3%+$2.260
other213.7 hrs 38.1%-$38.880

The reversal_signal_bail group nets to roughly breakeven — the position-watcher's exit logic (3 of 4 reversal signals against the trade) is doing its job there. The real damage is the sl_hit group: same weak entry signature (only 44.7% favorable reach), but the watcher didn't catch these in time, so they ran the entire remaining distance to the stop — the single biggest loss source in the strategy, at -$23.71.

Bug 2 — no limit on repeated entries during a losing streak

Because BreakoutLevel recalculates fresh every M15 bar from a rolling 10-bar window, a sustained one-directional move can look like a brand-new breakout on every subsequent bar. On 2026-07-27 — breakout's single worst trading day, -$41.96 net — the strategy tried to open 10 fresh EURUSD SELL positions in a row, ~15 minutes apart, over more than 3 hours:

10× EURUSD SELL, NOT_ENOUGH_MONEY / ORDER_REJECTED, 2026-07-27 13:50–17:10
all rejected by the broker for insufficient margin — not by any check in the strategy itself

The position registry (internal/bot/registry.go) had no concept of "how many trades is this specific strategy already running" — only global and per-tier caps that don't distinguish which strategy owns an open position. The account running out of margin is what actually stopped the pileup, not the strategy recognizing it was already exposed to the same move.

Decision — implemented and shipped

Two-bar confirmation: the first M15 candle to close past the 10-bar range no longer trades immediately — it's marked pending. Only if the next M15 candle's close is still beyond that same level does it fire. If price closes back inside the range, the candidate is discarded. All existing filters (H1 trend alignment, ADX ≤ 35, min SL/TP distance) re-run at confirmation time, not just at first detection.

Per-strategy position cap: CanOpen now caps any single strategy at 2 concurrent positions, counted live off the registry on every signal — applies to every strategy, not just breakout, so it also guards against the same pileup happening anywhere else.

The fix, in code
// Confirmation: don't fire on the first bar, mark it pending instead.
s.pendingDir = dir
s.pendingLevel = m15.BreakoutLevel
s.pendingBarTime = m15.BarTime
return hold("breakout detected — awaiting next-bar confirmation")

// Next bar: only fire if price is still beyond the same level.
held := (dir == config.SignalBuy && m15.Close > level) ||
    (dir == config.SignalSell && m15.Close < level)
if !held {
    return hold("breakout not confirmed — price closed back inside the range")
}
// registry.go — new per-strategy cap, checked alongside the existing global/tier caps
if strategyCount >= maxPerStrategy {
    return false, "max positions for this strategy reached"
}

internal/strategy/breakout/strategy.go and internal/bot/registry.go (maxPerStrategy = 2). Ships through the same feat → dev (squash) → main (merge) → tag flow as today's other fixes.

Part 5 — ema_pullback strategy
Same disease as breakout, worse: zero cooldown, and a trend label that never checks trend strength

Spotted while reviewing today's trades: ema_pullback had exactly 1 trade in its entire history before today (July, net -$13.46). Today it fired 12 trades in 90 minutes — all XAUUSD SELL, all clustered in a tight $7 band (4387–4394), almost all closing within 5 minutes via the same reversal-signal bail-out, net -$6.21 for the day, capped off by a real sl_hit for -$11.12 on the 12th.

Not the same bug as breakout — a different one

The per-strategy position cap shipped earlier today (Part 4) caps concurrent positions at 2. Checking the actual timestamps, 10 of these 12 trades never overlapped at all — each closed before the next opened. Only one pair briefly ran 2 at once, which the cap correctly allowed. The cap was never going to touch this: it's a strategy closing a position and immediately opening a near-identical new one minutes later, not a pileup. That needs a cooldown, not a concurrency limit.

Root cause: a trend label that's blind to trend strength

H1 ADX during the entire 90-minute window sat at 14–15 — well below any real trend threshold:

H1 barRegimeADXEMA9EMA21
12:00trending_down14.984381.844391.77
13:00trending_down14.264388.774395.22

CalculateRegime (internal/indicator/regime.go:9-42) takes an adx parameter and never references it in the function body — the trending label is decided purely by whether EMA fast sits meaningfully below/above EMA slow. A weak, sideways chop with a barely-tilted EMA reads exactly the same as a strong, ADX-confirmed trend. Other strategies here (breakout, dd_ranging_breakout, dd_early_breakout) all compensate by adding their own ADX filter on top of the regime label — ema_pullback never did, despite its entire thesis depending on a real trend existing to pull back into.

On top of that, it had no cooldown of any kind — not even the one-per-bar dedup breakout had before today's fix. Every ~5 minutes the M5/EMA-proximity conditions happened to align again, it fired a brand new trade with no memory of the one it just closed.

Decision — implemented and shipped

ADX floor: require h1.ADX ≥ 25 before trusting the trend label at all — same threshold other strategies here already use for "real trend."

One entry per H1 bar: the setup is built entirely off the H1 trend/EMA, so it can't meaningfully change more than once per H1 close. Would have capped today's 12 entries down to at most 2 (the window spanned two H1 bars).

The fix, in code
if h1.BarTime == s.lastEntryH1BarTime {
    return hold("ema_pullback already signaled this H1 bar")
}

if h1.ADX < adxTrendFloor {
    return hold("H1 ADX too weak — regime label isn't backed by a real trend")
}

internal/strategy/ema_pullback/strategy.go (adxTrendFloor = 25.0). Scoped to this strategy only — a general cross-strategy cooldown mechanism (for the sequential-churn failure mode specifically) is a separate follow-up, not yet designed.

Superseded by Part 6 below: the flat one-per-H1-bar cooldown shown above was replaced the same day with an outcome-aware version — see Part 6 for why and what changed. adxTrendFloor is unchanged.

Part 6 — Outcome-aware cooldown (general mechanism)
The flat H1-bar cooldown was too blunt — and the same problem turned up in strategies we hadn't looked at yet

Discussing the ema_pullback fix raised a fair objection: blocking any second entry within the same H1 bar can't tell a genuine repeat mistake from a legitimately different signal later in the same hour. A single loss is just a loss — it shouldn't cool anything down. Two consecutive same-direction losses, though, is a real pattern worth respecting.

The redesign

Replaced the bar-boundary cooldown with an outcome-aware one: a strategy now needs 2 consecutive same-direction invalidated closes before a 60-minute cooldown kicks in for that direction only — the opposite direction is never blocked. Classification is by close reason, not raw P&L, since a reversal-bail can close a few cents positive by luck while the setup was still wrong:

Close reasonWhat it meansCounts as invalidation?
sl_hitStopped out — thesis was wrongYes
regime_against / rsi_against / etc.Watcher's own indicators flipped against it fastYes
time_stop=...Never showed any favorable movement at allYes
tp_hitFull target reached — thesis validatedNo — resets streak
peak_drawback=NN%Ran into real profit first, gave some back — direction was rightNo — resets streak
breakeven_slMoved into profit enough to arm break-even — direction had meritNo — resets streak
eod_closeSession housekeeping, unrelated to setup qualityIgnored

Built as internal/strategy/close_reason.go (a ClassifyCloseReason function shared by the whole strategy package, not duplicated per-strategy) plus an optional OutcomeAware interface (internal/strategy/strategy.go) that any strategy can implement via OnClosed(side, closeReason string, closeTime time.Time). The bot type-asserts for it in notifyStrategyClosed (internal/bot/bot.go), called from both close paths right after a position leaves the registry — strategies that don't implement it are completely unaffected.

Also centralized 8+ scattered raw-string close-reason literals ("sl_hit", "regime_against", the dynamically-formatted peak_drawback=%.0f%%, etc.) across bot.go/watcher.go into named constants in the same file — the classifier and the code that builds these strings now share one source of truth, so they can't silently drift apart.

Checking who else has this problem

Before applying this anywhere else, queried every strategy's trade history for the same pattern: a new signal firing within 30 minutes of a same-direction invalidated close from the same strategy, then compared that group's P&L against everything else:

Biggest surprise: trend_follow — the one strategy with a clear proven edge (+$151.50 net) — is being dragged down by exactly this pattern. Its 48 clean trades average +$3.44 each; its 75 chained re-entries average -$0.41 each. The strategy's overall profit is happening despite this drag, not because of it. dd_ranging_breakout shows the literal opposite, which is why it was deliberately left alone rather than applying the fix everywhere uniformly.

Decision — implemented and shipped

Outcome-aware cooldown added to ema_pullback, breakout, trend_follow, and rsi_reversal — the four strategies with real evidence of the drag. dd_ranging_breakout, sr_bounce, session_momentum, and session_open deliberately left untouched — no evidence, or evidence pointing the other way.
