Key Findings
What We Discovered
1. XAUUSD broker SL/TP was never set since gold was added
Critical Bug

All XAUUSD market orders opened with no broker-native SL or TP. The code used absoluteSLTP=true for gold and sent absolute prices to fields 10/11 — but cTrader docs explicitly state absolute SL/TP is not supported for MARKET orders. The broker silently ignored both fields.

This was masked because the bot's internal watcher monitored price on every tick and called closeTrackedPosition when SL was reached — making it look like SL hits were broker-driven when they were actually internal.

Root cause of previous relative failure: An earlier attempt at relative SL/TP for XAUUSD used slDist * priceDivisor where priceDivisor=100 for gold (2 decimal places). The cTrader API requires 1/100000 units. Sending slDist * 100 instead of slDist * 100000 made the SL distance 1000× too small — broker rejected with INCORRECT_BOUNDARIES. This was misread as "broker rejects relative for gold" and the code switched to absolute, which is worse.
Proof from Aug 10 data: Position 236061302 had max_favorable = 4364.85 vs TP = 4360.33 — price went 4.52 pts through the TP level but the broker never closed it. If broker TP were set, it would have closed at 4360.33.
2. close_reason was always a guess, never real
Data Integrity

inferCloseReason(grossProfit) returned "tp_hit" if profit ≥ 0, "sl_hit" if loss. This was pure guesswork — a position closed by break-even SL at a tiny profit was labeled "tp_hit". A position closed by peak_drawback at a gain was also "tp_hit". Historic close_reason data in the DB cannot be trusted.

3. Peak_drawback was closing winners in the 50–70% zone
Strategy Calibration

Old arm threshold: 50% of TP distance. On Aug 10, all 4 peak_drawback closures had peaks in the 51–64% range — just barely over the arm threshold. At that early stage, a 60% drawback of a tiny local peak is a normal candle wick, not a reversal signal.

Post-close candle analysis (M5, 4h window):
  • 236020316: closed +$6.96 → lowest after = 4316.57 (would have hit break-even SL)
  • 236054545: closed +$2.50 → lowest after = 4342.51 (would have hit break-even SL)
  • 236059838: closed +$2.63 → lowest after = 4347.79, highest = 4391.75 (would have hit TP)
  • 236061302: closed +$2.97 → lowest after = 4350.95, highest = 4395.36 (would have hit TP)
Peak_drawback saved 2 positions from going to break-even SL but cut 2 winners that would have hit full TP.
4. Break-even stop confirmed working on first production trade
Confirmed

Position 235964932 (sr_bounce BUY EURUSD) closed at exactly 1.15531 — the amended break-even SL. The position_adjustments table recorded old_sl=1.15461, new_sl=1.15531, reason="break_even". The broker enforced the amended SL via ProtoOAAmendPositionSLTPReq (2110). After close, price continued down to 1.15480 — confirming the break-even saved what would have been a loss.

Peak drawback analysis — would SL or TP have been hit?
sql
SELECT p.provider_position_id, p.open_price, p.current_sl, p.current_tp,
       f.execution_price AS closed_at, f.net_profit,
       MIN(c.low) AS lowest_after, MAX(c.high) AS highest_after,
       CASE
         WHEN p.side = 'BUY' AND MAX(c.high) >= p.current_tp THEN 'TP would have hit'
         WHEN p.side = 'BUY' AND MIN(c.low)  <= p.current_sl THEN 'SL would have hit'
         ELSE 'still between SL and TP (4h window)'
       END AS what_happened_after
FROM positions p
JOIN orders o ON o.id = p.our_order_id
JOIN signals sig ON sig.id = o.signal_id
JOIN fills f ON f.our_position_id = p.id AND f.close_reason IS NOT NULL
JOIN candles c ON c.symbol_id = p.symbol_id
  AND c.period = 'M5'
  AND c.bar_time > p.close_timestamp
  AND c.bar_time <= p.close_timestamp + INTERVAL '4 hours'
WHERE p.open_timestamp >= '2026-08-10 00:00:00+03'
  AND p.open_timestamp <  '2026-08-11 00:00:00+03'
  AND p.provider = 'ctrader'
  AND f.close_reason LIKE 'peak_drawback%'
GROUP BY p.provider_position_id, p.open_price, p.current_sl, p.current_tp,
         p.close_timestamp, p.side, f.execution_price, f.net_profit
ORDER BY p.close_timestamp;
Break-even trades — did price continue to old SL?
sql
SELECT p.provider_position_id, sig.strategy, p.side,
       p.open_price, pa.old_sl, pa.new_sl AS breakeven_sl,
       p.max_favorable, f.execution_price AS close_price,
       f.gross_profit, f.close_commission AS commission,
       f.close_reason,
       CASE
         WHEN p.side = 'BUY'  AND f.execution_price <= pa.old_sl THEN 'would have hit old SL'
         WHEN p.side = 'SELL' AND f.execution_price >= pa.old_sl THEN 'would have hit old SL'
         ELSE 'old SL was NOT hit'
       END AS verdict
FROM position_adjustments pa
JOIN positions p ON p.id = pa.position_id
JOIN orders o ON o.id = p.our_order_id
JOIN signals sig ON sig.id = o.signal_id
LEFT JOIN fills f ON f.our_position_id = p.id AND f.close_reason IS NOT NULL
WHERE pa.reason = 'break_even'
ORDER BY pa.adjusted_at DESC;

Fix: replace inferCloseReason with classifyBrokerClose. Old function just checked grossProfit >= 0. New method compares execution price against tracked position's SL and TP prices (within 5-pip tolerance) and checks BreakEvenActive.

go — close reason logic
func (b *Bot) classifyBrokerClose(tracked trackedPosition, execPrice float64) string {
    tol := 5 * b.pipSize

    if tracked.BreakEvenActive {
        beSL := tracked.OpenPrice + 2*b.pipSize // BUY
        if tracked.Side == config.SignalSell { beSL = tracked.OpenPrice - 2*b.pipSize }
        if math.Abs(execPrice-beSL) <= tol { return "breakeven_sl" }
    }
    if tracked.SLPrice > 0 && math.Abs(execPrice-tracked.SLPrice) <= tol { return "sl_hit" }
    if tracked.TPPrice > 0 && math.Abs(execPrice-tracked.TPPrice) <= tol { return "tp_hit" }

    // Fallback: direction from open price
    if tracked.Side == config.SignalBuy && execPrice > tracked.OpenPrice { return "tp_hit" }
    if tracked.Side == config.SignalSell && execPrice < tracked.OpenPrice { return "tp_hit" }
    return "sl_hit"
}
Why: historic close_reason data was meaningless. "breakeven_sl" is now a distinct reason separate from "sl_hit".
