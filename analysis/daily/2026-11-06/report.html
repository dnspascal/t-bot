4 · Data bug
Live candles were saved with close = low
The bug
Since first commit

While a candle is still forming, cTrader sends its updates inside ProtoOASpotEvent with low, deltaOpen and deltaHigh, but no deltaClose (field 7). The decoder computed Close = low + deltaClose, and with field 7 missing deltaClose stayed 0, so close = low. When a new candle started, the bot saved the last update of the previous one, so every live candle on every timeframe was saved with close = low. Only the history loaded at startup (GetTrendbarsRes, which includes field 7) was correct. Monthly checks showed close = low on 99–100% of candles since Jun/Jul.

5 Nov 04:00 H1OpenHighLowClose
Saved4088.54135.14084.34084.3
Real4088.54135.14084.3≈4124.6

A ~36-point rally hour was saved as a down candle.

Impact by strategy
Re-check after deploy
  • Hardly affected: EMA-vs-EMA comparisons (trend_follow, the regime classifier). Both lines shift down by about the same amount.
  • Affected: price-vs-EMA checks (ema_pullback), RSI levels (dd_oversold_bounce, rsi_reversal), candle colour and momentum (session_momentum), and ATR.
Fix
On dev · 00c8d96

When a live candle has no close, the bot uses the bid from the same price update, kept within the candle's low–high range. Candles that do include a close (history loaded at startup) are unchanged.

// internal/provider/ctrader/api/proto.go — decodeLiveTrendbarEvents
+ if bar.closeMissing && bid > 0 {
+     bar.Close = math.Min(math.Max(bid, bar.Low), bar.High)
+ }

Tests in proto_test.go use the 5 Nov 04:00 candle. Without the fix they fail with close = 4084.3.
