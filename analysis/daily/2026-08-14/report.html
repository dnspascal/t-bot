Why a higher gate makes it worse, not better

The intuitive read — "70% is a stricter bar, so it should be a more validated signal" — turns out backwards for this specific mechanism. minPeakGain doesn't validate a trade; it selects which trades the 60%-giveback rule gets evaluated on. A trade that reaches 70% of the way to TP before pulling back is already a stronger, more advanced trade than one that only reached 50%. And a pullback close to the target is statistically more likely to be normal consolidation before the trend continues than a genuine reversal — a standard pattern in trending price action. A trade that stalls at just 50% progress and pulls back is showing weaker conviction to begin with, so cutting it is a cheaper, more justified call. Raising the gate shifts the population toward exactly the trades where a pullback is least likely to mean "it's over."

No change shipped to peakDrawbackThreshold or the gate itself today — n=6 is too thin to act on. This section documents the finding and the reasoning; Part 5 is the actual fix, which is about making this kind of check possible without git archaeology next time.

Part 5 — Decision parameter tracking (implemented and shipped)
Every position now snapshots the watcher-level constants that governed it, so this never has to be reconstructed by hand again

Getting the numbers in Part 4 required manually walking git log -p for internal/bot/watcher.go, matching diffs to commits, then commits to deploy tags, to figure out which gate value applied to which historical trade. Slow, and one wrong commit match away from silently repeating the exact mixing-regimes mistake this whole investigation started from.

Scope — and why this doesn't turn into a column per feature

Deliberately limited to the shared, watcher-level knobs — the ones that silently reclassify how every open trade, across every strategy, gets judged the moment they change. Per-strategy SL/TP/entry constants are a much larger surface (13 strategy files, many knobs each) and are already reasonably scoped by strategy name + code history since they change less often; left untracked for now.

One JSONB column rather than a dedicated column per parameter — adding, renaming, or retiring a tunable is a code change, not a migration, and no dead schema is left behind if a mechanism like peak-drawback ever gets dropped entirely. Any future "did closing early cost us a winner" analysis should filter on this field (e.g. WHERE decision_params->>'peak_drawback_gate_pct' = '70') instead of treating all-time history as one uniform population — that's the actual lesson from Part 4.

Can't backfill history that predates this column — every trade before today stays NULL, which is the honest state (unknown provenance), not a gap to paper over. Every trade from today onward is self-describing.

Part 6 — Should the reversal-signal close require multi-candle confirmation?
Simulated it against real historical price data — both N=2 and N=3 make outcomes worse, not better

Raised concern: a single M5 candle where 3+ of the 4 reversal signals flip against a position might just be noise, since the signals are correlated (all derived from the same bar). Proposed fix to test: require the "3+ against" condition to hold on N consecutive M5 bars in a row before actually closing — any bar where it drops back below 3 resets the counter to zero.

Simulated directly against real data rather than guessing: market_states stores the exact per-bar regime/rsi/ema_fast/ema_slow/momentum_direction values the live bot used — the same fields countReversalSignals reads — so every historical reversal-closed trade's signal sequence can be replayed bar-by-bar, not approximated. Real SL/TP touches (from candle high/low) are checked at each bar too, since a broker-side stop would trigger before the watcher's next bar-close check either way.

Validation: N=1 replay reproduces the actual historical close time (within 10min) for 144 of 156 trades (92%) — the 12 misses are the separate signalsToReduce tier-based partial-close path, which this simulation doesn't model. Core mechanism replay confirmed trustworthy.

Verdict — don't add confirmation delay, and why

Of the 152 trades that close via reversal signal today, only 3–4 actually benefit from waiting. More than twice as many (6–11) get worse — they ride into a real SL that the fast exit would have avoided. The remaining ~140 barely change outcome at all; they just pay a small delay cost for nothing.

This matches Part 3's independent finding: the reversal mechanism is correctly identifying doomed trades most of the time (52–62% would've hit SL if left alone). The "confirming" second and third bar is usually bad news continuing to develop, not noise reverting — so waiting for it gives real reversals more room to hurt before exiting, rather than filtering out false alarms. Single-bar close is the better-performing version of this mechanism. No change made.

The third match (f82071f7) led to a real code bug, found while explaining the anomaly Fixed

That trade reached a genuine 188.1-pip peak, yet closed via time_stop=never_profitable_30m — a name that implies a 30-minute ceiling — after being open 27 hours (2026-07-27 01:20 → 2026-07-28 04:21). The underwater transition my script detected (19:40 on 07-27) sits 4 minutes after deploy tag v202607271640 (19:36:53) — a redeploy landed mid-trade.

checkTimeStop (internal/bot/watcher.go:283) reads pos.MaxFavorable straight from the in-memory registry. reconcileOpenPositions (internal/bot/bot.go:280), which re-registers every still-open position after the process restarts, never copied p.MaxFavorable/p.MaxAdverse from the DB row it already has in hand. PositionRegistry.Register seeds an unset peak to the position's open price rather than leaving it at zero — one notch less severe than "reset to zero," but the effect is the same defect: any real peak reached before a restart is discarded and replaced with "as if it opened right now," for every position that survives a deploy.

What isn't fully confirmed: the reset alone should make neverProfitable true almost immediately after restart (open price ≈ open price, trivially "never moved"), so the mechanism doesn't yet fully explain why this specific trade's actual close waited until 04:21 the next morning rather than firing within minutes of the 19:36 deploy — there may have been additional deploys in that window, or another gate in the call path not traced here. The reset-on-reconcile bug itself was confirmed by reading the code and is fixed below regardless of that remaining gap; f82071f7's exact 9-hour timeline stays a partially open question.

The fix Fixed

Added candle.Repository.Since(ctx, symbolID, period, since) (internal/candle/repository.go) — fetches real candle history from a given time forward, ascending. reconcileOpenPositions now calls a new Bot.recoverPeaks helper before registering each rediscovered position: walks the real M5 candle closes from the position's true open_timestamp up to now and recomputes its actual peak-favorable/peak-adverse, mirroring PositionRegistry.UpdatePeaks's own convention of using candle close, not intrabar wicks.

maxFavorable, maxAdverse := b.recoverPeaks(ctx, p.SymbolID, p.Side, openPrice, openTime)
b.registry.Register(trackedPosition{
    // ...existing fields...
    MaxFavorable: maxFavorable,
    MaxAdverse:   maxAdverse,
})

Falls back to (0, 0) — and from there to Register's existing open-price seed — if no candle history exists yet (a position reconciled within its first M5 bar) or the candle query fails, so a restart can never leave a position worse off than the pre-fix behavior, only better informed when history is available. No schema change, no new write load — read-only against candle data already being collected for every other purpose in this codebase.

Verdict

No dedicated stagnation-timeout mechanism needed — the anecdote that prompted this check doesn't generalize, and the genuine pattern is rare (3 trades, ever). The existing 30-min never-profitable time-stop plus the reversal-signal mechanism already cover the realistic cases now that the reconcile-time peak loss is fixed.
