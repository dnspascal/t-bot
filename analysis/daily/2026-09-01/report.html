Part 1 — Live risk incident
XPDUSD SELL opened with a real, valid stop-loss distance — and no stop-loss on the broker

Flagged live: an open XPDUSD SELL showed a TP in the cTrader app but the SL column was empty — just an info icon. Ask price had already run past where the intended SL should have been, with the position still open. Recommended an immediate manual close/SL while investigating.

SL/TP sent as a distance from the price at signal time, not the actual fill price Fixed

Confirmed via server logs (slDist:2.021994819548354 in the "placing order" line) that the stop distance sent to the broker was only ~$2.02 — smaller than the live spread (~$5.58) at the time. cTrader silently drops a stop that tight rather than erroring the whole order, so the market order filled with no SL attached at all. Root cause: SLPips/SLPrice are computed relative to the price at signal-evaluation time, but the broker applies the distance to the real fill price — if price moves (or spread is wide) between decision and fill, the effective stop shrinks. Compounded here by XPDUSD's M15 ATR still being immature so soon after the symbol's own onboarding.

Decision — implemented and shipped

Right after fill, re-anchor to the strategy's own intended absolute SL/TP (already correct in our DB), apply a minimum-distance floor relative to the real fill price, and push it as an explicit AmendPositionSL — the same amend path already proven for break-even adjustments — instead of trusting the market order's relative fields.

internal/bot/bot.go (recordOpenFill). PR #51, tag v202608270239.

Known limitation: the pre-existing open position wasn't retroactively protected by this fix — it had to be closed manually.

Part 2 — Restart-attribution bug
A strategy explicitly excluded from the shared exit watcher got closed by it anyway — because a restart erased its name

Checking today's trades, an ema_pullback position closed via regime_against,rsi_against,ema_cross_against — the shared reversal-watcher's exit reason. ema_pullback.UsesTrendWatcher() has returned false since Aug 26 specifically because this watcher's logic doesn't suit counter-trend strategies. That should have been architecturally impossible.

"3+ signals confirmed — closing position" — posID 238767407, 03:25:17 EAT, confirmed live in tbot@xpdusd.service journal output, for a position whose strategy is ema_pullback.
server log, cross-checked against signals.strategy via the DB
Startup reconcile never restored trackedPosition.StrategyName Fixed

usesTrendWatcher(strategyName) looks up the strategy by name and defaults to applying the watcher for any name it doesn't recognize — a reasonable-looking safe default. But OpenByProvider, the query startup reconcile uses to reload open positions after a restart, never selected a strategy name at all — every reconciled position got registered with StrategyName: "", which always falls into that "unknown, apply the watcher" branch. This bot deploys many times a day, so any position open across a restart was silently exposed — regardless of what its own strategy had explicitly opted out of.

Same mechanism explained a second, independent-looking symptom: dd_oversold_bounce's live P&L (-$0.38 over 16 trades) looked flat despite a backtested win rate matching its real one closely. Broken down by close reason, 10 of 16 trades (62.5%) closed via this exact watcher path — every one of them before this fix.

OpenByProvider now joins orders/signals to recover the real strategy name, so reconcile restores it correctly. Part 3 — Dashboard
"Today" showed yesterday's trades for the first 3 hours of every EAT day

Reported directly: tbot.denismgaya.com showing trades from the previous calendar day under "Today." The API's day boundary is Africa/Dar_es_Salaam (UTC+3); the dashboard's isoDate() used Date.toISOString(), which is UTC. Between 00:00–03:00 EAT every day, the UTC calendar date is still yesterday's — exactly the window this was caught in.

Decision — implemented and shipped

isoDate() now formats via Intl.DateTimeFormat('en-CA', {timeZone:'Africa/Dar_es_Salaam'}) to match the API's own boundary. Single fix point — the only UTC-date usage in the frontend.

t-bot-web/src/app/_components/dashboard.tsx. Separate repo, pushed straight to main (Vercel auto-deploys from there, no dev branch in this repo).

Part 5 — Break-even mechanism
A trade closed "at breakeven" for -$0.07 — and on gold specifically, that's closer to a coin flip than a guarantee

Checked the specific flagged trade (gross +$0.01, commission -$0.08, net -$0.07) against the last 12 XAUUSD breakeven_sl closes vs EURUSD's. EURUSD's were all net positive. XAUUSD's: 6 of 12 net negative, three with negative gross — meaning some had closed on the losing side of entry, not just failed to clear commission.

classifyBrokerClose's breakeven tolerance was wider than the actual buffer Fixed

The real buffer is 2 pips ($0.20 on gold). The classifier's tolerance for calling something "breakeven" was 5 pips ($0.50) — wide enough to mislabel a real loss (e.g. a BUY that closed $0.21 below open) as a breakeven exit. Replaced with the actual semantic definition: a break-even close can never be worse than the open price. Overshoot in the favorable direction (real slippage on a genuine stop) still counts.

Gold's tick noise blows through a flat 2-pip buffer before a stop confirms Fixed

Commission alone is ~$0.08/trade on gold. breakEvenBufferPips is now symbol-aware — XAUUSD raised to 5 pips; EURUSD and everything else keep the default that was already working there.
